MAESTRO

Route every task to the right model you already have.

Local or cloud, Maestro finds the models you can use (API keys, subscription logins, and models already served on your machine or network), scores them against public benchmarks and picks one per task. Free and open source. It runs on your machine, and your keys never leave it.

Two ways to use it

In your coding agent, or as your model provider

Same router, same model map. Use the skill when an agent splits up the work; use the endpoint when one client should talk to one URL and let Maestro choose.

As a skill

Use it in your coding agent

Claude Code, Codex, OpenCode, Gemini CLI, Cursor and other agents that support Agent Skills ask Maestro which model should take each subtask, then delegate to a subagent, another CLI or a local model.

  • No daemon, no network on the routing path: the decision is made on your machine
  • Picks a category for each subtask, then the seat you have for it
  • Tells the agent exactly how to delegate: subagent, CLI, local model or inline
Any harness that supports Agent Skills
$ npx skills add this-live/maestro-router
or the Claude Code plugin marketplace
$ claude plugin marketplace add this-live/maestro-router
$ claude plugin install maestro@maestro

Then tell your agent: "use maestro", "route this" or "use the right model". These two installs track the repository's default branch; the skills installer has no option to pin a release.

As an OpenAI-compatible endpoint

Use it as a model provider

maestro-router serve runs a local endpoint with a web dashboard. Hermes Agent, or any OpenAI client, sends everything to maestro/auto and Maestro picks the model per request.

  • Streaming, tool calls and images pass through; Anthropic models are translated both ways
  • Falls back to the next model on a 429, 5xx or timeout before the first byte
  • Agent loops stay on one model until a new user message arrives
Install from GitHub (not on PyPI yet)
$ pip install https://github.com/this-live/maestro-router/releases/download/v3.1.1/maestro_router-3.1.1-py3-none-any.whl
$ maestro-router setup
$ maestro-router serve --open

Clients connect to http://127.0.0.1:4545/v1; maestro-router hermes --install sets up Hermes Agent.

How it works

Detect, score, route

Maestro only routes to what you can actually run. It learns what you have once, scores it, and then makes each per-task decision locally, from a cached map.

1

Finds what you have

maestro-router detect and maestro-router discover look for API keys, subscription CLIs and model servers, and record what each can serve. Presence only: key values and login tokens are never read.

2

Scores it honestly

Benchmarks from a bundled models.dev snapshot become percentiles among recent models, blended with a prior from size, price and age, then a strength for each of the 11 jobs and a category.

3

Routes each task

The ladder maps job and difficulty to a category. Maestro picks a model you have that is good enough for that job, cheapest first by default, and says why in the decision.

What a coding agent sees (output trimmed)
$ maestro-router route --harness claude-code "why's the checkout test flaky"
{"job": "debug", "difficulty": 2, "confidence": 0.95, "needs": ["tools"],
 "category": "standard", "seat": "claude-code", "model": "sonnet",
 "delegate": {"kind": "subagent", "harness": "claude-code", "model": "sonnet"},
 "reason": "debug/d2 → standard; claude-code subagent available", ...}
What it finds

Every model you can already use

Maestro does not sell you models. It uses the ones you are already paying for, logged in to, or running yourself.

API keys

Any provider in models.dev

Any provider whose key is in your environment or in ~/.maestro/keys.env: Anthropic, OpenAI, Google, DeepSeek, xAI, Mistral, OpenRouter, Groq and the rest. maestro-router keys set stores one with hidden input.

Subscription logins

Claude Code, Codex, Gemini CLI

Maestro checks that you are logged in and uses those seats only through their official CLIs. Login tokens are never read or forwarded. In provider mode they serve chat, never tool calls or images.

Models you already serve

On this machine or your network

vLLM, SGLang, llama.cpp, LM Studio and Ollama, on localhost or a box such as a DGX Spark. Maestro never downloads, loads or starts a model: it routes only to what a server has already loaded.

Measured, and you can rerun it

How often it picks the right kind of model

The offline classifier sorts a task into a job and a difficulty, and the ladder turns those into a model category. These are its scores on 237 held-out prompts that it was not tuned on. The script and the prompts are in the repository, and CI fails if the scores drop.

Router eval: 237 held-out test prompts
80.2%job accuracy (11 jobs)
65.0%exact category
99.6%category within one step
8.0%under-routed (too weak)
0.0%severely under-routed

Offline rules classifier on the odd lines of evals/prompts.jsonl, tuned only on the other half. Routing one step too weak costs more than one step too strong, so most misses lean strong. Reproduce: python evals/run.py --classifier rules --split test.

Read these numbers with care. The prompts and their labels were written by an LLM and only partly checked by hand, and about 15% of them could fairly belong to two jobs, so a perfect router would not score 100%. They measure the classifier, not the quality of the answers you get back.
Coming next In shadow

Maestro S1, a tiny decision model

A small local model in pure Python that estimates a task's job, difficulty, need for tools, stakes and output size, then picks the seat with the best expected value given each model's odds of success, its price, your quota and the wait.

  • Runs in shadow today. The ladder decides; S1 logs what it would have picked, so you can compare before switching (decider: utility).
  • Quota-aware. A subscription window with slack costs nothing ("use it or lose it"); its price rises only when the burn rate would exhaust it.
  • Learns locally from your pass and fail outcomes, with guards, and maestro-router learn --reset undoes it.
  • Jev-compatible. POST /v1/systemone answers TypeSafe Jev's typed-decision format.
Your machine, your keys

Local-first, by design

Maestro is a program on your computer, not a service. There is no account and nothing to sign up for.

Keys stay in one file

Keys you add live in ~/.maestro/keys.env (mode 600). A key is sent only to its own provider and is never printed, logged or returned by any endpoint.

Logins are never read

Subscription logins are checked for presence only and used through their own CLIs. Their tokens are never read or forwarded.

Prompts are not logged

The request log keeps the model, job, category, latency and tokens. Prompt text is stored (first 120 characters) only if you set log_prompts: true.

Nothing phones home

No telemetry. A request goes only to the provider you route it to. The optional Jev classifier sends task text to TypeSafe only if you set TYPESAFE_API_KEY.

The server stays local

maestro-router serve binds to 127.0.0.1. Serving beyond loopback requires MAESTRO_API_KEY, and the dashboard needs an admin token and same-origin requests.

Your hardware, your call

Maestro never downloads, loads or starts a model. On a box that serves nothing, discover --local-fit suggests models that would fit, as advice only.

Dashboard

Get started

Install, set up, serve

Python 3.9 or newer. Nothing else to install, and no account.

  1. Install

    As a command, or as a skill for your coding agent (both use the same code):

    $ pip install https://github.com/this-live/maestro-router/releases/download/v3.1.1/maestro_router-3.1.1-py3-none-any.whl
# or from source
$ pip install git+https://github.com/this-live/maestro-router@v3.1.1
# or run it without installing
$ uvx --from git+https://github.com/this-live/maestro-router@v3.1.1 maestro-router route "fix the failing test"
# or, as a skill
$ npx skills add this-live/maestro-router

    The command is maestro-router because mobile.dev's Maestro (mobile UI testing) already uses maestro; add alias maestro=maestro-router to your shell profile if you want the short name. The skill install tracks the repository's default branch; the skills installer has no option to pin a release.

  2. Try a decision

    Works before any setup. It says which kind of model the task needs and which of yours would take it.

    $ maestro-router route "fix the failing test"

  3. Set up

    Detects your providers, adds keys with hidden input, asks about model servers you already run, and scores every model.

    $ maestro-router setup

  4. Serve

    Starts an OpenAI-compatible endpoint at http://127.0.0.1:4545/v1 and opens the dashboard. Any OpenAI client can then use the model name maestro/auto.

    $ maestro-router serve --open
$ curl -s http://127.0.0.1:4545/v1/chat/completions -H 'Content-Type: application/json' \
    -d '{"model": "maestro/auto", "messages": [{"role": "user", "content": "what is a mutex?"}]}'

    The response's model is the model Maestro chose, and the x-maestro-decision header says why. maestro-router hermes --install connects Hermes Agent.

Straight answers

What Maestro does not do

  • It is not a hosted service. There is no cloud version, account or paid plan. You run it on your own machine.
  • It does not give you models. It routes to the keys, logins and model servers you already have. With none of them, it can only tell you what a task needs.
  • It never downloads, loads or starts a model. A local model is used only if your server already has it loaded.
  • It does not judge the answers. It picks a model before the request is sent. The router eval above measures that choice, not the reply.
  • The decision model is still in shadow. S1 and expected-utility routing are off by default; the ladder decides.
  • Subscription seats are chat only in provider mode. Claude Code, Codex and Gemini CLI logins never take tool calls or images through maestro-router serve.
