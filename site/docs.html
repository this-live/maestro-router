Quick start

Install it one of three ways. All of them run the same code.

Any harness that supports Agent Skills (Claude Code, Codex, OpenCode, Gemini CLI, Cursor and others)
$ npx skills add this-live/maestro-router
Claude Code plugin marketplace
$ claude plugin marketplace add this-live/maestro-router
$ claude plugin install maestro@maestro

The skills installer and the plugin marketplace track the repository's default branch; the skills installer has no option to pin a release.

pip (gives you the maestro-router command; not on PyPI yet, so install from GitHub, pinned to the v3.2.0 release)
$ pip install https://github.com/this-live/maestro-router/releases/download/v3.2.0/maestro_router-3.2.0-py3-none-any.whl
# or from source:
$ pip install git+https://github.com/this-live/maestro-router@v3.2.0
# or, without installing:
$ uvx --from git+https://github.com/this-live/maestro-router@v3.2.0 maestro-router route "fix the failing test"

The command is maestro-router because mobile.dev's Maestro (mobile UI testing) already uses maestro; add alias maestro=maestro-router to your shell profile if you want the short name.

Then, for provider mode, the web UI and Hermes:

# detect providers, add keys (hidden input), add model servers you already run, score every model, connect Hermes
$ maestro-router setup
# http://127.0.0.1:4545/v1 for clients, and the web UI
$ maestro-router serve --open
# or paste the output of `maestro-router hermes --print` into ~/.hermes/config.yaml
$ maestro-router hermes --install

Without pip, run any command as python3 skills/maestro/scripts/maestro <command> from a checkout. maestro-router doctor shows what Maestro detected.

Use it as a skill

Inside a coding agent, tell it "use maestro", "route this" or "use the right model". For each real unit of work the agent runs maestro-router route, which classifies the subtask into one of eleven jobs and a difficulty from 0 to 3, picks a category from the ladder, and answers with JSON that says who should run it:

$ maestro-router route --harness claude-code "why's the checkout test flaky"
{"job": "debug", "difficulty": 2, "confidence": 0.95, "needs": ["tools"],
 "category": "standard", "seat": "claude-code", "model": "sonnet",
 "delegate": {"kind": "subagent", "harness": "claude-code", "model": "sonnet"},
 "reason": "debug/d2 → standard; claude-code subagent available", ...}
delegate.kindWhat the agent does
subagentUses its own subagent mechanism with that model (Claude Code: the Agent tool's model parameter).
localRuns argv, which calls maestro-router run on a local or network model, and uses the printed reply.
cliRuns another installed CLI headless (claude -p, codex exec, gemini -p, opencode run).
inlineDoes it itself: it is already on the right tier, or no better seat exists.

OpenCode and Gemini CLI delegate by category: run maestro-router install once to create their maestro-<category> subagents, and again after you change their models. maestro-router route --explain adds the classifier signals, the ladder cell and the tier walk.

Use it as a model provider

maestro-router serve runs a local OpenAI-compatible endpoint (default http://127.0.0.1:4545/v1) and the web UI. Point a client at it with the model name maestro/auto:

from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:4545/v1", api_key="anything")
r = client.chat.completions.create(model="maestro/auto", messages=[{"role": "user", "content": "why is my test flaky?"}])
print(r.model)   # the model Maestro chose
  • Per request, Maestro keeps the enabled models that can take it (tools, images, context window, quota), keeps those whose score for the job reaches the category's floor, and ranks them by expected cost, quota headroom and observed latency.
  • Streaming, tool calls, stream_options.include_usage and images pass through; Anthropic models are translated both ways.
  • Agent loops stay on one model. A request whose last message is a tool result reuses the model chosen for that conversation (keyed on X-Session-Id, or a hash of the system prompt and first user message; 30 minutes). A new user message is routed afresh.
  • Fallback. On a 429, 5xx, timeout or connection error before the first byte, the next candidate is tried (three at most) and the failing model cools down. The x-maestro-decision response header says what was chosen and why.
  • Subscription seats (Claude Code, Codex, Gemini CLI) serve chat only: never a request with tools or images.
  • Binding. 127.0.0.1 needs nothing. --host 0.0.0.0 requires MAESTRO_API_KEY in the server's environment; clients send it as Authorization: Bearer ....

The web UI link that maestro-router serve prints carries the admin token (kept in ~/.maestro/admin_token, mode 600).

Hermes Agent

maestro-router hermes --install appends the missing top-level blocks to ~/.hermes/config.yaml after making a backup; if a block already exists it prints it for you to merge, because Maestro does not rewrite YAML it did not write. maestro-router hermes --print prints this:

# Maestro as a custom provider for Hermes Agent (merge into ~/.hermes/config.yaml)
model:
  default: maestro/auto
  provider: custom
  base_url: http://127.0.0.1:4545/v1
  api_key: maestro  # placeholder: Maestro ignores it unless MAESTRO_API_KEY is set
  context_length: 128000
auxiliary:
  compression:
    provider: custom
    base_url: http://127.0.0.1:4545/v1
    api_key: maestro
    model: maestro/fast
  title_generation:
    provider: custom
    base_url: http://127.0.0.1:4545/v1
    api_key: maestro
    model: maestro/fast
  session_search:
    provider: custom
    base_url: http://127.0.0.1:4545/v1
    api_key: maestro
    model: maestro/fast
  vision:
    provider: custom
    base_url: http://127.0.0.1:4545/v1
    api_key: maestro
    model: maestro/auto
delegation:
  base_url: http://127.0.0.1:4545/v1
  api_key: maestro
  model: maestro/auto

Model names

NameWhat it does
maestro/autoClassifies the request and routes it.
maestro/<category>Fixes the category: maestro/local, fast, standard, strong or frontier.
maestro/<job>Fixes the job (maestro/code, maestro/debug, maestro/plan, ...); the difficulty still comes from the text.
<provider>/<model>Goes straight to that model (see GET /v1/models), with fallback to the next-best of its category.

The eleven jobs are plan, code, debug, review, ops, research, data, write, edit, summarize and ask.

Models you already serve: DGX Spark, vLLM, Ollama

Maestro never downloads, loads, starts or installs a model. It looks at what is already being served on this machine and on your network and uses exactly those models. Ollama (:11434), LM Studio (:1234), vLLM (:8000), SGLang (:30000) and llama.cpp (:8080) on localhost are found by themselves. For a box on your network, add it once:

# or answer the question in `maestro-router setup`; saved to local_endpoints
$ maestro-router setup --endpoint http://spark.local:8000
# scores what the Spark serves ("spark: serving 1 model (gpt-oss-120b) - using these")
$ maestro-router discover

The same thing in ~/.maestro/config.json (vLLM has to listen beyond localhost, --host 0.0.0.0, for other machines to reach it; it serves one model per port, so add one entry per port):

{"local_endpoints": [{"name": "spark", "url": "http://spark.local:8000", "kind": "openai"}]}
  • Installed is not served. Ollama and LM Studio load models on demand, which can run a machine out of memory, so Maestro asks which models are loaded and routes only to those (unless you set "local_allow_load": true).
  • Strength from size by default: under 10B serves local cells, 10B to 40B up to fast, 40B or more up to standard. Change it with local_models or pin models under models.local.
  • Chat-only jobs. A plain local model takes ask, summarize, write, plan and data when the task needs no repo tools; repo jobs use it only when your harness runs it natively as a subagent.
  • Suggestions only when nothing is served. maestro-router discover --local-fit lists open-weight models that would fit a box's memory, with a serve command. That is advice: Maestro prints a command and stops.
  • maestro-router detect --scan probes your own /24 subnet for Ollama and OpenAI-compatible servers, only when you ask; --save adds what it finds. MAESTRO_NO_SCAN=1 forbids it.

Config basics

Optional ~/.maestro/config.json (MAESTRO_HOME moves the directory). Every key is optional; maestro-router config prints the effective config. A few you are most likely to want:

KeyDefaultMeaning
max_tier"frontier"Never route to a cloud model above this, e.g. "strong".
prefer_localtrueUse local and network models for the jobs they can do.
local_endpoints[]Model servers on your network, as above.
objective"balanced""cost" (cheapest that works) or "quality".
ladder{}Override rows of the job by difficulty table, e.g. {"ask": ["local", "fast", "fast", "standard"]}.
models{}The model per harness and category; maestro-router models set codex.fast gpt-6-luna edits one cell.
log_promptsfalseKeep the first 120 characters of each prompt in the request log.
privatefalseOnly local models (or the calling agent) see tasks.
decider"ladder""utility" lets Maestro S1 and the expected-utility ranking pick the seat (S1 runs in shadow otherwise).

Privacy and security

  • Detection checks that API key variables, keys.env entries and login files exist; subscription logins are never read or forwarded.
  • A key is read only to authenticate to its own provider and is never printed, logged, returned by an API or stored anywhere but ~/.maestro/keys.env (mode 600).
  • The request log (~/.maestro/maestro.db) keeps no prompt text unless you set log_prompts: true.
  • The only third party Maestro talks to on its own is the optional Jev classifier, and only when you set TYPESAFE_API_KEY: it sends the task text (up to 4,000 characters) and the names and descriptions of your candidate models. Use --classifier rules to keep every task local.
